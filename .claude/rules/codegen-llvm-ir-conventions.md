# Codegen LLVM IR Conventions

### emitArithmeticOp dispatch order: new type-specific branches go BEFORE the str-vs-non-str reject

`emitArithmeticOp` ends with a str-vs-non-str reject as its last line of defense, but `isStringValue()` returns true for any `ptrTy_` value without `hasAnyMeta()` — effectively "unknown pointer". Branches added AFTER the reject are unreachable for metadata-less pointer operands. Insert new type-specific branches (List concat, Map merge, Set union, etc.) BEFORE the reject. Use typed metadata accessors (`getMapKeyType` / `getListElementType` / etc.), not `isStringValue`. Current order: low-level / `**` / string concat / List+List / Map+Map / Set+Set / mixed-collection reject / str-vs-non-str reject / `//`+`/`+`%` / `+`-`*`.

### Bool reject in arithmetic / bitwise must be at each operator branch entry, not at function entry

`promoteToInt` and `promoteToFloat` silently widen `i1` (bool) via ZExt / SIToFP. Any arithmetic / bitwise branch that calls them — or `CreateSIToFP` directly — must call `rejectBoolInOperator(v, op, "arithmetic"|"bitwise")` first. Do NOT gate inside `promoteToInt` / `promoteToFloat` themselves (ARC and string-repeat paths intentionally widen i1). Do NOT gate at function entry either: `emitArithmeticOp` processes string concat / repeat (`"x" + true` auto-stringifies — must keep working) and collection-concat BEFORE numeric branches, so a top-of-function reject would break legal expressions. Place `rejectBoolInOperator` at the entry of each numeric / bitwise branch (`**`, `//`, `/`, `%`, default `+`-`*`, `emitBitwiseOp`).

### in / not in dispatch order: user overload → Set → Map → List → str → error

The str branch must come AFTER Set/Map/List because `isStringValue(container)` returns true for any `ptrTy_` value without collection/resource metadata. Set/Map/List headers all have `hasAnyMeta() == true` so `isStringValue` correctly excludes them; placing str earlier would fire on plain `str` RHS before collection branches even run. When RHS is `str` and LHS is `any`, unwrap with `unwrapFromAny(elem, ptrTy_)` (no `wrapInAny` direction needed — str has no element type to promote into). Other LHS types vs str RHS: emit a clear compile error.

### Opaque-pointer codegen: `getUnqual` for pointer types, element-typed `CreateLoad`

Under opaque pointers every codegen-emitted pointer is the untyped `ptr` (the C++ counterpart of the FileCheck-golden rule just below). Build pointer types with `PointerType::getUnqual(*ctx_)` — the cached `ptrTy_` initialized in `src/codegen.cpp` — never a typed `PointerType::get(elem, ...)`. Because a `ptr` carries no pointee type, every `CreateLoad` must pass the element type explicitly (`CreateLoad(type, ptr, name)`); the single-argument form cannot recover it. The codebase follows this uniformly — pointer construction goes through `getUnqual` and all loads are element-typed — so a stray typed pointer or single-arg load is a regression to reject, not a style choice.

### FileCheck goldens (`tests/filecheck/*.ry`)

Each file is both Ry source and a FileCheck script. Use `# CHECK:` (Ry comment is `#`, never `//`). Goldens run on unoptimized IR (`alloca`/`store`/`load` for every arg are present, `mem2reg` has not run). All pointer types are `ptr` under opaque pointers — never `i64*` / `i8*`. ARC retain/release only appears in CoW clone, lambda capture, and `@parallel for` paths — pick simple goldens accordingly. Result layout: `%Result = type { i1, i64, ptr }`. Goldens are LLVM-version-sensitive — re-verify after LLVM bumps. CI job is `continue-on-error` (advisory) but fix failures before merge anyway.

**Verifying a pure refactor is IR-byte-identical** (e.g. a module split / rename with no behavior change — #2025): capture `./build-rust/ry --emit-llvm-ir <file>` before and after and `diff`. The only legitimate difference is the **ASLR-randomized `__ry_arc_counter_address`** baked into `atomicrmw add ptr inttoptr (i64 <addr> to ptr)` (it varies per `ry` process; the goldens already mask it via `{{[0-9]+}}`). Normalize it before diffing — e.g. `sed -E 's/inttoptr \(i64 [0-9]+ to ptr\)/inttoptr (i64 ADDR to ptr)/g'` — or the diff shows false positives on every ARC path. After normalization the diff must be empty across the filecheck fixtures (and `ry_tests` + `ry test -p` must stay green) for the refactor to qualify as behavior-preserving. **Capture the final before/after diff *after* applying `rustfmt` / `clippy --fix`, not before**: migrating an extern body into a more deeply-nested `impl EmitCtx` method (the #2059–#2063 abi/ffi/core series) pushes long lines (e.g. a `c"…".as_ptr()` argument) past the width limit, so rustfmt re-wraps `.as_ptr()` onto a continuation line — source-layout-only and IR-neutral, but a diff captured pre-fmt is stale once fmt rewrites the file (#2061). **Probe-input resolution trap (#2082)**: repo throwaway files are banned, so a multi-path probe lives under `/tmp/`. But `./build-rust/ry --emit-llvm-ir /tmp/probe.ry` (file argument) resolves the **global** `~/.ry/` stdlib — `/tmp` has no `package.toml` ancestor, so the project-local `[paths]._dev_stdlib` (`share/std/`) is bypassed — and an older global stdlib silently lacks renamed symbols (a probe with `from json import load` died with `'load' not found in module 'json'` because the global release still exported the pre-#1887 `loadAs`). Feed the probe via **stdin from the repo root** instead: `./build-rust/ry --emit-llvm-ir -c < /tmp/probe.ry`. CWD-anchored dev-stdlib resolution then applies (matching how in-repo files like `examples/*.ry` resolve), and the stdin form also dodges a hang — `ry -c "$(cat file)"` reads code from *stdin* (the `"$(…)"` arg is ignored) and blocks waiting on it if the harness auto-backgrounds the command, whereas `-c < file` hits EOF and runs foreground-clean.

**Extracting a shared helper from near-duplicate emission blocks (the #2026 dedup) must preserve every SSA value name byte-for-byte — including the named-vs-unnamed asymmetry.** LLVM value names appear verbatim in textual IR and unnamed values are auto-numbered, so flipping one named value to unnamed (or vice versa) renumbers every downstream unnamed value and the diff is no longer empty even though the IR is semantically identical. Concrete trap from `emit_list_grow` (`crates/emit/src/composite/header.rs`, shared by `ry_emit_collection_append` / `_insert`): the `cap > 4` compare is named `cap_gt4` in append but left **unnamed** in insert. A naive `prefix`-derived helper that names (or prefixes) both breaks bit-exactness. Pass the divergent name as an explicit param (`gt4_name = c"cap_gt4"` for append, `c""` for insert) and derive the rest from a `prefix` arg via `cname_pfx`. SSA-name-stable helpers like the libc emitters (`emit_malloc` takes the result `name`; `emit_memcpy` / `emit_memmove` / `emit_free` are unnamed at every site) and `emit_any_retain_guard` (names identical across wrap / unwrap / try_unwrap, only the pointer differs) extract cleanly.

**The empty-diff is only meaningful if the changed path is actually emitted in the baseline** (a coverage gate, not just a diff). An untaken emission path yields a *false pass*: grep the baseline IR for each block's marker before trusting the diff. For the #2026 surface that means a single probe exercising `append` / `insert` / `removeAt` (grow → `app_doubled` / `ins_doubled`, shift → `memmove`), a heap collection **and** a str boxed into `any` (retain-guard → both `arc_hdr_from_data` and `str_hdr_from_data`), a shared-then-mutated collection (CoW → `cow_new_data`), and a ≥2-arg runtime call (`ry_emit_runtime_call` arg-buffer). The filecheck fixtures alone do not emit the list-grow / CoW paths. **Constant operands are a coverage trap too (#2092)**: a variadic-fold probe written with literal args (`sum(1, 2, 3)`) emits *no* `add` / `select` at all — `LLVMBuild{Add,FAdd,ICmp,Select}` fold to a constant when every operand is a `ConstantInt` / `ConstantFP`, so the path is silently uncovered and a buggy port would pass the empty diff. Force the arithmetic to emit by seeding the operands from non-constant loads (`x = 1; y = 2; sum(x, y, …)`), then grep for the op marker (`sum_v` / `mm_cmp` / `mm_best`) in the baseline. **A shared call-emission helper that branches on return type and/or calling convention is a multi-cell coverage trap (#2099)**: `emitLambdaCall` has six emitted cells — three calling-convention layouts (uniform `{thunk,env}` / plain no-capture / captured `{fn_ptr,caps}`, markers `uc.thunk` / a direct `@__lambda.N` call / `lcall.fn`) × two return shapes (non-void vs `isVoidTy()` → `emitCallIndirect(…, "")`). A probe of only value-returning closures (predicates, transforms) silently skips all three **void** cells, so a botched void port would pass the empty diff. Force the void cells with a `fn(int) -> Unit` parameter invoked inside a fn (uniform void) and a block-body `(x: int): return` lambda on a List `tap` with and without a capture (plain / captured void), then grep the baseline for `call void %uc.thunk` / `call void @__lambda.` / `call void %lcall.fn` before trusting the diff. The same "enumerate every layout×shape cell, marker-confirm each" rule applies to the follow-on `emitLambdaCall`-site migrations (#2100 and the dense-iterator sweep).

**Do not assume a Rust `core::*` helper reproduces its C++ `CodeGen::*` namesake's instruction order (#2092).** `composite::header::load_list_header` (`crates/emit/src/composite/header.rs`) emits the three header geps first, then the three loads (grouped: `gep len_ptr` / `gep cap_ptr` / `gep data_ptr` / `load len` / `load cap` / `load data`), whereas `CodeGen::loadListHeader` (`src/codegen_call.cpp`) interleaves them (`gep len_ptr` / `load len` / `gep cap_ptr` / `load cap` / `gep data_ptr` / `load data`). The two are NOT byte-identical. A migration whose baseline used `loadListHeader` (e.g. the `sum` list form) must reproduce the **interleaved** order inline — six `LLVMBuildStructGEP2` / `LLVMBuildLoad2` calls in gep,load,gep,load,gep,load order, names `<prefix>_len_ptr` / `_len` / `_cap_ptr` / `_cap` / `_data_ptr` / `_data`, with `cap` loaded-but-unused to match the C++ helper — NOT call `core::load_list_header`. Always confirm against the baseline IR before assuming any core helper matches its C++ counterpart's order.

### emitStringByteLen requires StringHeader-backed handles

`emitStringByteLen(handle)` reads `handle - 8` (STRING_BYTELEN_OFFSET). Safe only when `handle` came from `cachedGlobalString`, `buildArcGlobal`, or a runtime path that called `makeString` / `makeStringUninit`. `IRBuilder::CreateGlobalString` produces a plain `[N x i8]*` global without a StringHeader prefix; passing it to `emitStringByteLen` reads 8 bytes of unrelated global data as `byte_len`. Always use `cachedGlobalString` for new str constants in codegen. Raw `CreateGlobalString` is safe only for printf-style format strings that are never read back as Ry str handles.

### Collection ops on pointer elements: positive allowlist via list_elem_type_name

When a collection helper's pointer-element branch uses `strcmp` (or any C-string op), guard with a positive allowlist on `list_elem_type_name`, not a single-field blacklist via `getNestedListElementType`. The `NestedListElem` field is set only by `propagateTypeMeta`'s isListTypeName branch; Map/Set/function element kinds live in `map_value_type_name` / `list_elem_fn_type_info`. Blacklist on a single field is structurally incomplete — `List<Map<K,V>>` / `List<fn(...)>` / `List<Set<T>>` slip through and `strcmp` on Map/Set/closure headers is UB. Pattern: classify pointer elements as "non-str" if `list_elem_type_name` is non-empty and not `"str"`, OR if `nested_list_elem != nullptr`, OR if `list_elem_fn_type_info.has_value()`; emit "operation only supported for primitive / str lists". Resource lists (`List<TcpStream>`) get a non-empty type name and are caught. For Set elements (`toContain` / `toNotContain` Set branch and similar helpers), apply the analogous classification using `set_elem_type_name` and `set_elem_fn_type_info` — `ValueMetadata` has no `nested_set_elem` field, so the disjunct collapses to two: `set_elem_type_name` non-empty and not `"str"`, OR `set_elem_fn_type_info.has_value()`. Sets of nested collections still flow through these two fields via `propagateTypeMeta`.

### emitRuntimeError terminates its block — caller pre-splits to continue

`emitRuntimeError` emits `fprintf(stderr, ...)` → `exit(1)` → `unreachable` and does NOT switch to a fresh dead block. If the caller continues emitting IR in the same block, those instructions land after `unreachable` and LLVM verify rejects them. Treat `emitRuntimeError` like `CreateRet` / `CreateBr`: split into err / ok BBs before the call, set insert point to `errBB`, emit error, then set insert point to `okBB` for the happy path. Canonical examples: `emitIntZeroDivGuard`, `?` operator path in `emitExprVariant(ErrorPropagateExpr)`.

### Lowering constant-fold and emission must agree on integer interpretation (i1 sext vs zext)

When a lowered op (`include/ry/codegen/lowered_*.hpp`) splits into a compile-time constant-fold branch (lowering side) and a runtime IR-construction branch (emission side), both must interpret each ConstantInt operand the same way. If emission ZExt-extends `i1 → i64` (so `true` becomes `1`), the lowering fold must read `i1` operands with `getZExtValue()` — switching to `getSExtValue()` only for widths > 1. `getSExtValue()` on `i1` returns `-1` for `true`, which silently wraps to `len - 1` in fold but emits `1` at runtime, breaking the bit-exact extract that the lowering/emission split is supposed to preserve. Canonical example: `lowerBoundsCheck` (`src/codegen_lowering_bounds_check.cpp`) keeps `getSExtValue()` for wider widths and switches to `getZExtValue()` when `getBitWidth() == 1`, mirroring `emission::emitBoundsCheck`'s `CreateZExt(idx, i64Ty_)`. Apply the same rule to any future `lowering::lower<Op>` that constant-folds two ConstantInt operands.

### ARC weak_count: a non-atomic read paired with atomic RMW writes is a TSan race even on the release path

`weak_count` is mutated by `weak_retain` / `weak_rel` (`src/codegen_arc.cpp`) using `atomicrmw Add/Sub Monotonic` regardless of the surrounding op's atomic mode. Reading the same slot with a plain `CreateLoad` from another path (e.g. the release-time "should I free?" decision in `ry_emit_arc_release`) is therefore a data race per the C++ memory model — even when reasoning suggests the read can't observe a torn value, the mismatch between atomic and non-atomic accesses on the same address is itself UB and TSan flags it. Rule: any read of `weak_count` (or any field updated by `atomicrmw` elsewhere) must use an atomic load whose ordering scales with the caller's atomic mode (`AtomicOrdering::Acquire` when atomic, `NotAtomic` otherwise — `emitAtomicI64Load` collapses to a plain load when ordering is `NotAtomic`, preserving the non-atomic codepath byte-for-byte). The strong_count immortal check in the same function already follows this pattern (`Monotonic` when atomic, `NotAtomic` otherwise); apply the same shape to weak_count and to any future readers of atomically-updated ARC header fields. Canonical example: `ry_emit_arc_release` weak-count read at `crates/emit/src/composite/arc.rs` (#1968 self-review fix; the `lib.rs` monolith was split per responsibility in #2025).

### Atomic primitives are generic LLVM ops; ordering / binop selection stays C++-side (#2190)

The `ry_emit_atomic_rmw` / `ry_emit_atomic_load` / `ry_emit_atomic_cmpxchg` primitives (added for weak ARC migration) live in `crates/emit/src/primitive/ops.rs` because their signatures take `RyAtomicBinOp` and `RyAtomicOrdering` enums — LLVM-native vocabulary that names no Ry concept. The caller (C++) picks the ordering (`SeqCst` for retain/release weak_count, `AcquireRelease/Monotonic` for the weak-upgrade CAS, `Acquire` for the strong_count read paired with atomicrmw writes) and the binop (`Add` / `Sub`), keeping the Ry semantic decision where it belongs. This mirrors pilot D's `ry_emit_intrinsic_call`: a single generic primitive whose Ry-level shape (`Intrinsic::ID`, ordering enum) is selected by the C++ caller before crossing the boundary.

`ry_emit_atomic_load`'s `alignment` parameter follows a deliberate convention: `alignment == 0` skips `LLVMSetAlignment`, leaving the `LLVMBuildLoad2` default in place — this matches the C++ `CreateLoad + setAtomic` baseline (`align 4` on the host datalayout for i64). Callers that need an explicit alignment (e.g. for SIMD or aligned-attribute requirements) pass a positive value. `atomicrmw` and `cmpxchg` take no alignment knob — LLVM auto-computes from the datalayout (`align 8` for i64) matching the C++ `MaybeAlign()` baseline. Cmpxchg result values are auto-numbered (the LLVM C API `LLVMBuildAtomicCmpXchg` accepts no name); the primitive's `name` parameter is preserved for API symmetry but currently ignored — the C++ baseline `CreateAtomicCmpXchg` likewise produces an unnamed SSA result, so this preserves bit-exactness without future-callers needing to know.

The existing composite-internal helpers `emit_atomic_i64_load` and `emit_arc_counter_delta` (both in `composite/arc.rs`) stay pub(crate) and continue serving the inline ARC retain/release paths — the new primitives are an additional surface, not a replacement. A future sweep MAY migrate those internal helpers onto the primitives; the discipline is "one new generic op covers all current and future atomic-RMW / atomic-load / CAS callers", not "rewrite existing composite code." Out of scope for #2190 by explicit decision; the composite paths remain bit-exact.

When adding a future caller that needs a different ordering (e.g. `Release` for a one-way fence on shutdown) or a different binop (`XOR` / `AND` / `OR` for bitset state), extend `RyAtomicBinOp` / `RyAtomicOrdering` rather than adding a new primitive — the engine-side `to_llvm()` mapping in `primitive/ops.rs` is the only place that needs updating. The C-side enum order must match `RY_ATOMIC_*` constants in `abi.rs` and `api.h` (the cross-language parity discipline `tests/test_abi_layout.cpp` enforces for other enums; extending its coverage to atomics is a follow-on if drift becomes a concern).

### llvm_emit boundary helpers must derive parent function from the builder, not from ctx->function

In the `crates/emit/src/` emission modules (since #2025 the bodies live in per-op modules; #2109 split them into `composite/{arc,bounds,cast,collection,cow,any,option,result,reduce,header}.rs` and `primitive/{ops,function,control_flow,runtime_call,types,util,module,global,libc,error}.rs` over the layer-neutral `context.rs`), when an boundary helper creates new `BasicBlock`s, the parent function MUST come from `ctx->builder->GetInsertBlock()->getParent()`, NOT from `ctx->function` (the cached pointer set via `ry_emit_ctx_set_function`). The cached pointer reflects `cg.fn_` at set-time, but ARC / lambda / thunk / destructor / iterator-next codegen retargets `builder_` to a nested function without immediately mirroring that change into `cg.fn_`. Calling an boundary helper from one of those contexts then creates new BBs in the outer function while the builder appends instructions (CondBr / Br targets) in the nested function — LLVM verify rejects with `Referring to an instruction in another function!` (#1968). Existing helpers that follow this rule: `ry_emit_arc_retain` / `ry_emit_arc_release` (post-fix); `ry_emit_collection_append` / `ry_emit_collection_insert` / `ry_emit_collection_remove_at` (#1971; `ry_emit_list_slice` creates no new BBs so the rule trivially holds); `ry_emit_cow_ensure_unique` (#1970 — invoked from CoW paths that may be reached via lambda / `@parallel for` / nested-collection destructor sites); `composite::result::emit_result_branch` (#1968; since #2069 the BB scaffold lives in this `composite::result` free function — the IR was moved out of the `ry_emit_result_branch` abi extern, which now only resolves ids and builds the re-entrant callback closures — and it still derives the parent from the builder); `ry_emit_bounds_check` (#1996 — the last helper aligned onto this pattern). All BB-creating emitters (boundary helper or `core` engine method / free function) now derive the parent function from the builder, not from `ctx->function`; use the builder-derived form unconditionally for new ones too. The `ry_emit_ctx_set_function` boundary entry and the cached `ctx->function` field were removed in #2083 once every BB-creating emitter derived its parent from the builder — there is no longer a cached function field to read, so the builder-derived form is the only option (the `EmitCtx::new` constructor, the `ry_emit_ctx_create` C signature, and every C++ caller dropped the `function` argument; emitted IR is byte-identical).

### Re-entrant boundary callbacks move to `core` as a free function with closures, never a `&mut self` method

A boundary extern whose work includes a **re-entrant C callback** — one that calls back into the emitter through the abi boundary and re-enters `cx(ctx)` to get a fresh `&mut EmitCtx` (e.g. `ry_emit_result_branch`'s `RyBuildValueFn` ok/err builders, which recursively emit each arm's value) — must NOT relocate its IR into a `&mut self` `core` method. A `&mut self` method holds the receiver borrow for its whole body, *including across the callback call*; the callback's `cx(ctx)` then creates a second `&mut EmitCtx` aliasing the receiver across the extern call — UB under Stacked/Tree Borrows that the borrow checker cannot see (it crosses the FFI boundary). This is why #2060 left `result_branch` in `abi/`.

The fix (#2069, `composite::result::emit_result_branch` ← `abi/result.rs`): move the IR into a `core` **free function** that takes the **decomposed Copy handles** it needs (`builder: LLVMBuilderRef`, `context: LLVMContextRef`) plus the builders as `&mut dyn FnMut() -> ValueRef` closures — deliberately NOT `&mut self` and NOT a raw `*mut EmitCtx`. Holding no `&mut EmitCtx` borrow (only Copy LLVM handles + a borrow of the closure objects, which live on the abi stack), it can invoke the closures while the only live `&mut EmitCtx` is the transient one each closure forms on re-entry. This preserves the exact live-borrow timeline of the original abi free function (which extracted `b`/`context` up front and only re-borrowed via `cx(ctx)`/`resolve` transiently) — so an ASan/TSan-clean original stays clean. **Load-bearing abi-side detail**: each closure body must be two-step — call the callback, *then* `resolve` the returned id (`let id = build_ok(user_ctx); resolve(cx(ctx), id)`). Inlining `resolve(cx(ctx), build_ok(user_ctx))` re-introduces the alias: arguments evaluate left-to-right, so `cx(ctx)` forms the `&mut EmitCtx` borrow *before* `build_ok(user_ctx)` runs, holding it across the re-entrant callback. **#2081 made this two-step structural rather than evaluation-order-dependent**: the raw reify `cx` is now fully private to an `abi::ctx_access` submodule (the sibling op / result / lifecycle modules can no longer name it — a stray `cx(ctx)` there is a compile error), and every transient access goes through the scoped accessor `with_ctx(p, |c| …)`, whose `&mut EmitCtx` is bound to the closure body and cannot escape. So `do_ok` became `let id = build_ok(user_ctx); with_ctx(ctx, |c| resolve(c, id))` — the C builder runs *outside* any `with_ctx` by construction, so no borrow can span it regardless of evaluation order. Caveats `with_ctx` does NOT remove: it does not NULL-check (callers guard `p` first) and does not make aliasing *impossible* (nesting two `with_ctx` on one handle, or raw-casting the `&mut` out of `f`, still aliases; `checked_cx` likewise still returns an escaping `&mut`) — it confines the reify to one audited site and makes each borrow scope lexically visible, the "confined and locally auditable, not alias-proof" stance. One unsafe-block subtlety it forces: an `unsafe fn`'s implicit body-unsafe does NOT reach into a nested closure, but a lexical `unsafe { … }` block DOES — so the `with_ctx` closures sit inside an explicit `unsafe { … }` block and carry no inner `unsafe` (adding one trips `unused_unsafe` under `-D warnings`). The abi shell keeps the C signature, NULL guards, id↔value `resolve`/`intern`, and closure construction; `core` keeps every `LLVMBuild*` / BB op. Contrast `any_try_unwrap` (#2063), whose ok/err closures capture only Copy LLVM refs and are **not** re-entrant, so they migrate fully inside a `&mut self` method — re-entrancy is the discriminator, not the presence of closures.

### Rust mirrors of C++ header structs need a cross-language parity guard, not a "keep in sync" comment

The `emit` crate rebuilds the internal list/map/set/arc header structs on the Rust side to GEP and size them; their shape must match C++'s canonical `listHeaderTy_` / `mapHeaderTy_` / `setHeaderTy_` / `arcHeaderTy_` (`src/codegen.cpp`). Until #2071 the only protection was a `// Field order MUST stay in sync` comment — weaker than the boundary descriptors, which `tests/test_abi_layout.cpp` pins: nothing pinned the internal headers, so a C++ field-order change the Rust mirror failed to follow would compile, pass the layout test, pass the filecheck goldens (which don't emit the CoW Map/Set paths), and only corrupt CoW deep-copy at runtime. When you reconstruct such a header in Rust, two mechanical guards are mandatory:

1. **Single-source the shape + a cross-language parity test.** Define the field-kind list once (`crates/emit/src/context.rs` `header_fields`, driving both `build_header_struct` for emission AND the test-only `ry_emit_test_header_layout` extern in `crates/emit/src/abi/test_introspect.rs`), and assert it against the canonical C++ types read from a real `CodeGen` (`tests/test_header_layout.cpp`: field count + per-index type + ABI size). A Rust-only `#[cfg(test)]` self-check is **insufficient** — each side would only validate against its own constants, so a C++-only reorder trips no guard (the same "compare directly, don't self-check" lesson as the boundary's #1995 residual-gap note in `docs/architecture/llvm-ir-emission-boundary.md`; and CI's `lint` job runs no `cargo test`, so a Rust unit test would not even be gated — see `.claude/rules/tests-cpp-conventions.md`). Keep the extern reading only the pure-data `header_fields` slice, never `build_header_struct`, so `crates/emit/src/abi/` stays clear of the `scripts/check-emit-abi-no-ir.sh` gate.
2. **Behavioral same-type-swap coverage.** All header fields are 8 bytes (i64 / ptr), so a same-type swap (`len↔cap`, `keys↔vals`, `strong↔weak`) is invisible to any layout/offset check — only exercising the deep-copy and reading back lengths AND values catches it (`tests/spec/cow.test.ry`, run under ASan: a `keys↔vals` / `elems↔buckets` swap also trips the str retain loop on a non-pointer field). Harmful same-type swaps are exactly the behaviorally-catchable ones; symmetric swaps round-trip and are benign. The parity test's per-index type check still covers the cross-type reorders deterministically. ARC's `strong↔weak` leans on the existing dense ARC behavioral suite rather than a new test.

### A switch-path migration's coverage gate needs an explicit-value enum, and the name-array GEP folds to a ConstantExpr (#2100)

`str(List<enum>)`'s variant-name lowering (`src/codegen_tostring.cpp`) only takes the `CreateSwitch` path when the enum has `hasExplicitValues == true`; a value-less enum falls to the direct-GEP branch (`einfo.nameArray[val]` with `val` as a runtime index) and never emits a `switch`. A migration that adds switch primitives (`ry_emit_create_switch` / `ry_emit_switch_add_case`) must coverage-gate on an explicit-value enum (e.g. `HttpStatus` with `Ok = 200` / …) — grep the baseline for `switch i64` / `vts.enum.merge` / per-variant case BBs before trusting an empty diff, exactly the false-pass trap the "empty-diff is only meaningful…" rule names. Second trap in the same path: the name-array GEP `CreateGEP([N x ptr], nameArray, {i64 0, i64 i})` has all-constant operands, so the IRBuilder folds it to a **ConstantExpr** inlined into the `load` operand — there is NO `enum_name_ptr` named instruction in the IR. The replacement `ry_emit_array_gep` (the two-index `{i64 0, idx}` primitive) folds identically, so its `name` argument is dropped and the diff stays empty; do NOT grep for an `enum_name_ptr` marker to confirm coverage (it is always absent regardless of migration) — grep the `switch` / case-BB markers instead.

### A variadic runtime call cannot migrate through `ry_emit_runtime_call` — carve it out and say so (#2100)

`ry_emit_runtime_call` builds its `FunctionType` as non-variadic. A migrated op whose body calls a **variadic** runtime symbol — e.g. `__ry_sprint_printf` (`getSprintPrintf()`, `isVarArg = true`) in the tostring sprint-buffer path — therefore cannot route that call through the boundary; the `builder_.CreateCall(spf, …)` stays C++-side. When a (ii) "zero `builder_.Create*`" migration leaves a variadic call behind, state the carve-out explicitly (it is an orthogonal capability — how varargs cross the boundary — shared by every caller of the variadic symbol, not an oversight) rather than letting "= 0" stand when it is "= 0 except the shared variadic call". The AC is "no `builder_.Create*` for the capability under test (switch / array GEP / loop scaffold)", with the variadic mechanism named as out of scope.

### A hash-lookup migration is a two-cell coverage trap: hash path AND linear-scan path (#2101)

`emitSetElementLookup` (`src/codegen_builtin.cpp`) branches on element type: primitive elements (`int` / `str` / `float` / `bool`) take the **hash path** (`emitHashTableLookup` → `__ry_ht_find_*`, marker `ht_lookup_idx`, plus `key_ext` for the `Set<bool>` i1→i64 zext), while composite elements (`StructType` records, nested `List` / `Map` / `Set`, `any`) take the **linear-scan path** (markers `slin_cp` / `slin_cand`, plus `slin.any.eq` for the `Set<any>` `__ry_any_eq` compare). A probe of only `Set<int>` silently skips the entire linear-scan path, so a botched scan-scaffold port would pass the empty diff — the same multi-cell trap as #2099's `emitLambdaCall` layouts. Coverage-gate **both** cells: `Set<int>` / `Set<str>` / `Set<float>` (hash), `Set<bool>` (hash + zext, the only `key_ext` source), `Set<any>` (linear + `__ry_any_eq`), and `Set<record>` or `Set<List<…>>` (linear + `emitComparisonOp`), grep each marker in the baseline before trusting the diff. The blast radius is wider than the representative op — `emitSetElementLookup` / `emitHashTableLookup` are shared by set literal / `add` / `remove` / `in` / `contains` / `union` / `intersection` / `difference` and (via `emitMapKeyLookup`'s hash path) `Map` lookup — but the coverage requirement is **branch-coverage of the migrated functions** (every element-type cell: primitive-hash / `bool` zext / `any` / composite), not a per-caller probe. A single `isSubset` / `isSuperset` / `Map`-index probe with varied `Set<T>` element types reaches every branch; the un-migrated callers then emit the now-byte-identical shared helper while their own scaffolds stay untouched, so they need no separate probe. (When you DO add a `builder_.Create*`-zero AC, grep by the migrated functions' *current* boundaries — `grep -n 'CodeGen::emitSetElementLookup\|CodeGen::emitMapKeyLookup'` — not a line range from a pre-edit read, since inserted comments shift the end of each function.) The element comparison (`emitComparisonOp`) and the header load (`loadSetHeader` / `loadMapHeader`) stay C++-side by design (separate compare / header-load capabilities); the AC is "zero `builder_.Create*` in the lookup scaffold + hash-find", with the compare named as the out-of-scope carve-out (the #2100 "= 0 except X" discipline).

### An LLVM intrinsic-call migration must use NON-CONSTANT operands in the coverage probe — the helper's own APInt constant-fold path (not LLVM's IRBuilder folding) silently bypasses the migrated emission (#2102)

`emitIntOverflowCheck` (`src/codegen_arith.cpp`) takes both operands at compile time when each is a `ConstantInt`, evaluates the overflow check via `llvm::APInt::{sadd,ssub,smul,umul}_ov`, and either folds to `ConstantInt::get(result)` or fires a compile-time `codegenError("integer overflow")` — *no* `Intrinsic::getOrInsertDeclaration` / `CreateCall` / `CreateExtractValue` is reached on this path. This is *separate from*, and runs *before*, the IRBuilder-level constant folding the #2092 rule warns about (`LLVMBuild{Add,FAdd,ICmp,Select}` folding `ConstantInt` operands into a `ConstantExpr`). A probe written with literal operands (`3 + 5`, `7 * 2`) therefore emits **zero** `@llvm.sadd.with.overflow` / `@llvm.umul.with.overflow` / `_ov` / `_val` / `_flag` / `.overflow_err` markers in the baseline, and the migrated-vs-baseline `--emit-llvm-ir` diff is empty for the wrong reason — a botched `ry_emit_intrinsic_call` / `LLVMIntrinsicGetType` port would pass. Force the non-constant path with **function-parameter operands** for both the signed class (`fn signedOps(a: int, b: int) -> int: a + b; a - b; a * b; -a`, which reaches `codegen_expr.cpp:323` unary-neg + `codegen_expr.cpp:1436–1438` binary `+/-/*`) and the unsigned class (`fn umulOps(xs: List<int>) -> List<int>: xs.map(...); xs.filter(...)`, which reaches `codegen_call_higher_order.cpp:40,167,252,728,855` collection-alloc `umul_with_overflow`), then grep each marker in the baseline before trusting the diff. Both classes share the helper body, so migrating `emitIntOverflowCheck`'s 5 non-constant lines migrates *all 10 call sites* implicitly — the coverage requirement is the two classes (signed × `sadd/ssub/smul/neg`, unsigned × `umul`), not a per-site probe. The sibling helpers `emitCheckedArithmetic` (`Result<T, Error>` arm) and `emitSaturatingArithmetic` mul path inline their own `getOrInsertDeclaration + CreateCall + 2 × ExtractValue` and do *not* share `emitIntOverflowCheck`'s body; they are out-of-scope carve-outs for the #2102 migration, and a follow-on sweep migrates them using the same single-primitive discipline (`ry_emit_intrinsic_call` + `ry_emit_extract_value`).

### `emitRuntimeError` and `bounds_error` look alike but differ in BOTH global shape and instruction order — don't reuse one helper for the other (#2097)

C++ `emitRuntimeError` (`src/codegen_call_user.cpp`) gets its fprintf format string from `cachedGlobalString` → `buildArcGlobal` (`src/codegen.cpp`), which constructs a **StringHeader-prefixed** global `{ i64 ARC_IMMORTAL, i64 0, i64 byte_len, [N+1 x i8] data }` named with a `.arc` suffix, then passes a ConstantExpr in-bounds GEP `[0, 3, 0]` into the data payload to fprintf. The instruction order is **stderr load → fprintf → stdout load → fflush stdout → fflush stderr → _Exit → unreachable** (stdout's load is interleaved AFTER the fprintf call). `emitBoundsError` is a thin wrapper over `emitRuntimeError`, so its baseline IR inherits both properties.

But the Rust boundary helper `bounds_error` (`crates/emit/src/composite/bounds.rs`) — landed in #1996/#2060 — builds a **plain `[N+1 x i8]`** global via `get_or_create_msg_global` (no struct prefix, no `.arc` suffix, fprintf receives the bare global pointer), and loads stderr / stdout **adjacently** before the fprintf call. Both deviations were absorbed in that migration; the `--emit-llvm-ir` baseline did not pin them and the filecheck goldens only assert the `index.oob:` / `index.ok:` BB labels, not the global shape or load order.

That hidden divergence is the trap: a new `emitRuntimeError`-flavored migration that copies `bounds_error`'s shape — the obvious "same shape" choice — silently produces `@.foo` (plain) instead of `@.foo.arc` (str-handle struct) AND reorders the stdout load, breaking bit-exact parity with the C++ baseline (both the `@*.arc` GlobalVariable lines and the fprintf-vs-stdout-load ordering inside every fail BB). For an `emitRuntimeError`-shaped exit, use `get_or_create_arc_msg_global` (`crates/emit/src/composite/arc.rs`) — it mirrors `buildArcGlobal` exactly (struct prefix, `.arc` name suffix, ConstantExpr GEP into the data payload) — AND author a **dedicated** `runtime_error_with_*_arg` free fn that preserves the C++ `emitRuntimeError` instruction order (load stderr → fprintf → load stdout → fflush stdout → fflush stderr → _Exit → unreachable). Do NOT call into `bounds_error` from the new helper. Dedup caches stay independent — `bounds_msg_cache` for plain globals, `arc_msg_cache` for str-handle globals; both key on message bytes. Canonical example: `crates/emit/src/composite/cast.rs::checked_fp_to_int` + `runtime_error_with_value_arg` (#2097, the `emitCheckedFPToInt` migration).

This is the `load_list_header` lesson (#2092) applied to a second pair of look-alike helpers: don't assume two helpers that "do the same thing in C++" produce byte-identical Rust IR — confirm against the baseline. The same discipline applies to any future migration of `emitIntZeroDivGuard` / `emitIntDivOverflowGuard` and similar `emitRuntimeError`-callers (`src/codegen_call_user.cpp`).

### 条件分岐先でしか使われない値は target BB 内で emit する (lazy default rule)

**Source**: #2132 (2026-06-14, fix)
**Tags**: codegen, branching, PHI, lazy-evaluation, short-circuit, conditional-emission, emitCollOp_get

PHI の片方の incoming にしか使われない値は、 その predecessor BB に `SetInsertPoint` した後で `emitExpr` する。 分岐前の dominator block で emit すると、 他方のパスを通った場合でも IR 上は無条件に評価されるため、副作用付き式 (関数呼び出し、リソース確保等) が常に走る。 Canonical example は `emitCollOp_get` (`src/codegen_call_collection.cpp`) の 3-arg path: `emitExpr(*e.args[2])` と coerce ブロックを `builder_.SetInsertPoint(notFoundBB)` / `SetInsertPoint(oobBB)` の後に置く。 同じ原理は将来の 3-arg overload (例: `pop(list, default)`, `find(list, pred, default)`) や、 条件分岐先でしか値が要らない他の codegen 局所にも適用する。

PHI の predecessor (`notFoundEndBB` / `oobEndBB`) は `emitBranchUncond(mergeBB)` の **後**に `builder_.GetInsertBlock()` で再キャプチャすること。`default` 式が内部で新 BB を生成する場合 (`and`/`or` 短絡、ネスト `get`、`if expr`)、事前にキャプチャした BB ハンドルでは LLVM verify が PHI predecessor 不一致で reject する。

参照パターン: 2-arg get の `oobBB` / `notFoundBB` 内 `buildNoneValue` 構築 (同ファイル `emitCollOp_get` 2-arg arm)、`and` / `or` 短絡評価 (`src/codegen_expr.cpp` の `sc.rhs` BB 内で rhs を emit)。

### Fixed

- Overloaded function calls with no matching argument types now produce a canonical diagnostic at the frontend instead of leaking through to the LLVM IR verifier. Previously `for x in range(1..n): ...` (where `1..n` is a `List<int>`, not an `int`) crashed with `IR verify error: Both operands to a binary operator are not of the same type!`; it now reports `error: no matching overload for \`range\`` followed by the candidate signatures (`range(int) -> List<int>`, `range(int, int) -> List<int>`, `range(int, int, int) -> List<int>`) and the actual call types (`but called with: range(List<int>)`). The same canonical format is now used across all three dispatch paths: `range`/`len`/`enumerate` inline custom emitters, `@native` table-driven calls (e.g. `pow(1, 2.0)` mismatches), and user-defined function overload resolution (including ambiguous calls). (#1577)
